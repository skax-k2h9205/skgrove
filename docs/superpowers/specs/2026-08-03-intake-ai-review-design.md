# 대나무숲 접수 AI 사전 검토 — 설계

작성일: 2026-08-03

## 배경

지금은 접수 화면에 쓴 내용이 그대로 리더 관리함으로 간다. 사이에 아무것도 없다.

두 가지 문제가 있다.

- **읽는 쪽 부담.** 리더가 하루에 여러 건을 읽는데, 인신공격이 섞인 글은 사안을 파악하기 전에 감정을 처리해야 한다. 이 피로가 쌓이면 응답이 늦어지고, 응답이 늦으면 사람들이 쓰지 않게 된다.
- **용도 이탈.** 대나무숲이 특정인을 비방하는 통로가 되면 갈등을 줄이려던 도구가 갈등을 만든다.

목표는 검열이 아니라 **전달 가능한 형태로 만들어 보내는 것**이다. 사실 주장과 개선 요구는 그대로 두고, 사람을 향한 공격 표현만 걷어낸다.

## 범위

**한다**

- 접수 제출 직전(`review` 단계)에 LLM으로 본문을 검토
- 욕설·인신공격이 지적되면 **수정해야 제출 가능**
- 다듬은 문장을 제안하고, 사용자가 그대로 쓰거나 직접 고칠 수 있게

**안 한다**

- 캔미팅 의견, 유머게시판, 메시지, 안건 등록 — 접수 화면만
- 제3자 실명 노출 판정 (리더가 조치하려면 누구 얘긴지 알아야 한다. 비방과 다른 문제다)
- 서버 측 재검증 (아래 "알려진 한계" 참조)
- 검토 결과의 저장·통계

## 결정 기록

논의 중에 두 번 방향을 바꿨다. 나중에 "왜 이렇게 됐지"를 다시 묻지 않도록 남긴다.

| 결정 | 선택 | 이유 |
|---|---|---|
| 차단이냐 조언이냐 | **차단** | 처음에는 "욕설만 차단, 인신공격은 조언"으로 잡았다. 원문 제출 경로를 남기면 비방 통로가 되는 것을 막지 못한다는 판단으로 뒤집었다 |
| 검토 결과 기록 | **아무것도 남기지 않음** | "경고 무시하고 제출함"이 남으면 사실상 낙인이다. 익명 접수에 그런 꼬리표가 붙으면 사람들이 쓰지 않는다 |
| 판정 주체 | **LLM 단독** | 처음에는 "욕설=로컬 사전, 인신공격=LLM"으로 나눴다. 분리 근거가 "LLM에 차단권을 주지 않는다"였는데, 인신공격도 차단으로 정하면서 그 근거가 사라졌다. 사전은 `ㅅㅂ` 한 번에 뚫리는데 그 우회 표현은 LLM이 잡으므로, 사전이 잡는 것은 LLM이 잡는 것의 부분집합이다 |
| severity 단계 | **없음** | high/medium으로 나눠도 둘 다 수정해야 하면 구분이 무의미하다. 대신 **지적 기준을 높인다** — 문체 지적은 하지 않고 실제 공격 표현만 골라낸다 |

## 아키텍처

기존 캔미팅 AI 요약(`aiSummarize.ts` + `api/ai.ts`)과 같은 이음새 구조를 따른다. 키는 서버에만 두고, 프론트는 URL과 규격만 안다.

| 파일 | 역할 | 비고 |
|---|---|---|
| `api/review.ts` | OpenRouter 프록시. 프롬프트 보유 | `api/ai.ts` 패턴. `OPENROUTER_API_KEY` 없으면 휴면 |
| `src/intakeReview.ts` | 프론트 이음새. 요청·응답 정제 | `VITE_AI_ENDPOINT`와 별개인 `VITE_REVIEW_ENDPOINT` |
| `src/features/intake/ReviewGate.tsx` | 제출 전 확인 단계 UI | `Intake.tsx`가 이미 500줄 근처라 분리 |

`Intake.tsx`는 `ReviewGate`에 현재 값과 콜백만 넘긴다. 검토 상태는 `ReviewGate`가 갖는다.

## 데이터 흐름

`review` 단계 안에서 끝난다. 새 단계를 추가하지 않는다.

```
'제출 전 확인' 진입
   │
   ├─ 검토 요청 (8초 타임아웃, 실패 시 1회 자동 재시도)
   │    전송: { title, body, expectedChange }
   │    ※ 이름·메일·소속·익명 여부는 보내지 않는다
   │
   ├─ findings 있음 → 🚫 제출 불가
   │     [제안대로 수정] → 해당 필드 교체 → 재검토
   │     [내가 직접 고치기] → 작성 단계로 복귀
   │
   ├─ findings 없음 → 제출 가능
   │
   └─ 검토 실패 → 제출 가능 + 경고 배너
```

## LLM 계약

**요청**

```ts
POST {VITE_REVIEW_ENDPOINT}
{ title: string, body: string, expectedChange: string }
```

**응답**

```ts
{
  ok: boolean,
  findings?: Array<{
    field: 'title' | 'body' | 'expectedChange',
    kind: 'profanity' | 'personal-attack',   // UI 문구만 갈라진다
    reason: string,      // 왜 그렇게 읽히는지. 사용자에게 그대로 노출
    rewritten: string,   // 해당 필드를 통째로 대체할 완성 문장
  }>,
  reason?: string,       // ok:false일 때의 사유
}
```

`findings: []` 는 "지적할 것 없음"이다. `ok: false` 와 구분된다.

프론트는 `aiSummarize.ts`의 `sanitize()`와 같은 방식으로 응답을 정제한다. `field`가 세 값 중 하나가 아니거나 `rewritten`이 비어 있으면 그 항목을 버린다. 정제 후 항목이 0개면 "지적할 것 없음"으로 취급한다.

## 프롬프트 원칙

이 기능의 성패가 여기 걸려 있다. 원칙이 없으면 LLM은 "팀장이 회의에서 말을 자릅니다"를 "소통 방식에 개선의 여지가 있습니다"로 뭉갠다. 그러면 대나무숲이 무력화된다.

1. **사실 주장과 개선 요구는 건드리지 않는다.** 강도를 낮추지도, 완곡하게 만들지도 않는다.
2. 다듬는 대상은 **사람의 인격·능력에 대한 평가 표현**과 **욕설**뿐이다. 행동·영향·요구는 그대로 둔다.
3. **본인이 겪은 피해 진술은 인신공격이 아니다.**
   - `"저 사람은 무능하다"` → 인격 평가 → 지적
   - `"저 사람이 저에게 욕설을 했습니다"` → 사실 진술 → 지적하지 않음

   이 예외가 없으면 괴롭힘·갑질 제보가 통째로 막힌다. 이 도구가 가장 필요한 제보가 그런 것들이다.
4. 없는 내용을 지어내지 않는다. 완곡어법을 새로 채워넣지 않는다.
5. **지적할 것이 없으면 빈 배열.** 억지로 찾지 않는다. 문체·어투 지적은 하지 않는다.
6. 한국어로 쓴다. `rewritten`은 해당 필드 전체를 대체할 완성된 문장이다.

다듬기 예시:

```
원문:  김OO 과장은 무능해서 회의만 길어지고 팀에 민폐다
             ─────────                    ────────   ← 다듬을 것 (인격 평가)
       ─────────         ──────────────              ← 지킬 것 (사실·영향)

제안:  김OO 과장이 진행하는 회의가 자주 길어져 다른 일정에 영향을 줍니다
```

## UI 상태

`ReviewGate`가 갖는 상태는 넷이다.

| 상태 | 화면 | 제출 |
|---|---|---|
| 검토 중 | 스켈레톤 + "내용을 검토하고 있어요" | 비활성 |
| 지적 없음 | 조용히 통과. 별도 표시 없음 | 가능 |
| 지적 있음 | 항목별 카드: 사유 + 원문 + 제안. `kind`에 따라 문구 다름 | **불가** |
| 검토 실패 | 경고 배너 + [다시 검토] | 가능 (아래 참조) |

지적 카드의 버튼은 둘이다.

- **[제안대로 수정]** — 해당 필드를 `rewritten`으로 교체하고 재검토
- **[내가 직접 고치기]** — 작성 단계로 복귀. AI 제안이 사용자 의도와 다를 수 있으므로 반드시 있어야 한다

계속 막히는 경우를 위해 카드 하단에 안내를 둔다: *"이 내용이 꼭 그대로 전달되어야 하는 사안이라면 리더에게 1on1을 요청해주세요."* 앱이 받지 못하는 말도 사람은 받을 수 있어야 한다.

## 실패 처리

| 상황 | 동작 | 이유 |
|---|---|---|
| `VITE_REVIEW_ENDPOINT` 미설정 | 검토 없이 통과. 안내 없음 | "기능 없음"이지 "검사 실패"가 아니다. 로컬 개발에서 매번 경고가 뜨면 노이즈다 |
| 요청 실패·타임아웃(8초) | 1회 자동 재시도 → 그래도 실패하면 통과 + 경고 배너. 최악의 경우 약 16초 대기 | 여기서 막으면 AI 장애가 대나무숲 전체를 멈춘다 |
| 응답 스키마 불일치 | 정제 후 0개면 "지적 없음"과 동일 | `aiSummarize.ts`와 같은 규약 |

실패 시 경고 문구: *"AI 검토를 받지 못한 상태로 접수됩니다. 특정인을 향한 표현이 없는지 직접 확인해주세요."*

사용자가 이 경고를 보고 제출한 사실은 기록하지 않는다(결정 기록 참조).

## 프라이버시

- 요청 본문에 **이름·사내메일·소속 파트·익명 여부를 넣지 않는다.** 검토에 필요 없다.
- 검토 결과는 브라우저 메모리에만 존재하고 제출과 함께 사라진다. `Issue`에 필드를 추가하지 않는다.
- 제출 전 확인 단계에 항상 고지를 표시한다: *"다듬기 검토를 위해 작성 내용이 외부 AI로 전송됩니다. 이름·메일·소속은 보내지 않습니다."*
- OpenRouter 키는 서버 환경변수에만 둔다(`api/ai.ts`와 동일).

## 테스트

repo 관례대로 순수 함수만 테스트한다. 컴포넌트 테스트 인프라는 없다.

`src/intakeReview.test.ts`

- 엔드포인트 미설정 시 `{ ok: false, reason: 'disabled' }`
- HTTP 실패·비JSON 응답 시 `ok: false`
- `field`가 유효하지 않은 항목은 버린다
- `rewritten`이 빈 문자열인 항목은 버린다
- 정제 후 0개면 `ok: true, findings: []`
- `kind`가 두 값 중 하나가 아니면 `personal-attack`으로 강등(안전한 쪽)

프롬프트 품질(원칙 1~3을 실제로 지키는지)은 자동 테스트로 검증할 수 없다. 구현 후 아래 문장들로 수동 확인한다.

| 입력 | 기대 |
|---|---|
| `팀장이 회의에서 발언을 자주 끊습니다` | 지적 없음 (정당한 비판) |
| `김OO 과장은 무능해서 팀에 민폐다` | 지적 (인격 평가) |
| `김OO 과장이 저에게 욕설을 했습니다` | **지적 없음** (피해 진술) |
| `아 진짜 XX 짜증나서 못 해먹겠다` | 지적 (욕설) |

## 알려진 한계

- **클라이언트에서만 검사한다.** 개발자 도구로 우회할 수 있다. 앱 전체가 이미 클라이언트 신뢰 구조(`SECURITY-NOTES.md` 1·2번)라 여기만 서버 검증을 붙이는 것은 실익이 없다. 인증·RLS가 정리되는 시점에 함께 다룬다.
- **LLM 장애 시 필터가 없다.** 장애를 노리면 검토를 건너뛸 수 있다. 사내 도구라는 전제에서 감수한다. 막는 쪽을 택하면 AI 장애가 곧 접수 중단이 되고, 그쪽이 더 나쁘다.
- **오탐이 곧 침묵이다.** 지적 기준을 높이고 출구를 셋 두었지만(제안 수용 / 직접 수정 / 1on1 안내), LLM이 정당한 제보를 막을 가능성은 남는다. 운영하며 프롬프트를 조정해야 한다.
- **비용.** 접수 1건당 최소 1회, 수정 시 재검토마다 추가 호출이 발생한다. 접수량이 적어 문제되지 않을 전망이지만, 재검토는 사용자가 버튼을 눌러야만 일어나므로 자동 반복은 없다.

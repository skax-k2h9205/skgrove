# 익명 대나무숲 글 종단간(E2E) 암호화 — 운영자 불가독

- 날짜: 2026-08-14
- 브랜치: `feature/anon-encryption` (base: `origin/dev`)
- 상태: 설계 승인됨 (사용자)

## 배경 / 문제

대나무숲 접수(`issues`)는 익명글의 **작성자 신원은 저장하지 않지만**(`submitter_*`는 실명일 때만), **본문(`body`)을 평문으로 저장**한다. `issues` 테이블은 공개 anon 키로 통째로 SELECT 된다(실측: 10건 전부, "리더만 보기" 10건, 익명 4건, 조회코드 3건 노출). 즉 **JS 번들의 anon 키만 있으면 누구나 모든 대나무숲 글을 평문으로 덤프**할 수 있다. 비밀번호-초기화 때 서버 인증으로 옮긴 것과 같은 계열의 노출이다.

목표: **운영자(개발자·admin·커넥셔너 포함)도 DB에서 익명글 본문을 읽을 수 없게** 한다.

## 보장 범위 (위협 모델)

- **막는다**: anon 키 유출, DB 덤프·백업·로그의 수동적 열람, 운영자의 DB 직접 조회. 대상 리더 외에는 본문 복호화 불가.
- **못 막는다**: 운영자가 **악의적으로 프론트 JS를 교체**해 복호화 순간의 평문/리더 키를 탈취하는 능동 공격. 웹앱의 근본 한계이며(코드를 운영자가 서빙), 네이티브+재현가능빌드에서만 원천 차단된다. 본 기능은 이 한계를 문서화하고 **수동적 열람 차단**을 보장한다.
- **복호화 가능자 = 그 글이 지목한 대상 리더뿐.** admin/커넥셔너는 삭제만 가능, 열람 불가.

참고: GlobaLeaks(수신자 공개키 암호화 + 패스프레이즈로 감싼 개인키)를 표준 레퍼런스로 삼는다. SecureDrop(기존, 평문 수신 후 서버 암호화 → 서버 장악 시 평문 노출)이 반면교사.

## 결정 사항 (확정)

0. **적용 범위(v1)**: **익명(author='익명') 신규 접수만** 암호화한다. 실명 접수는 현행 유지(작성자가 자기 글을 다시 읽어야 하고, 신원이 이미 계정에 묶여 있어 위협 프로파일이 다름). 실명 "리더만 보기" 글의 데이터층 노출 차단은 후속 과제로 분리.
1. **복구**: 복구코드(리더 본인 보관). 개인키는 패스프레이즈·복구코드 **두 방식으로 각각 감싸** 저장하고 둘 중 하나로 복원. 운영자는 어느 쪽도 못 푼다.
2. **AI 검토**: 암호화된 글은 AI 검토(`/api/review`) **생략**.
3. **기존 데이터**: 신규 글부터 암호화, 기존 10건은 유지(이미 노출됨).
4. **대상 리더 키 미설정 시**: **평문 폴백(비반적)** — "암호화 미적용" 표시 후 현행처럼 평문 저장. 제출은 절대 실패하지 않는다.

## 암호 설계 (Web Crypto, 무의존성)

기존 `passwordHash.ts`가 Web Crypto(PBKDF2)만 쓰는 것과 같은 결로, 새 라이브러리 없이 SubtleCrypto만 사용한다.

### 리더 키페어
- **ECDH P-256** (`generateKey`, `deriveBits`). 공개키는 공개(JWK/base64), 개인키(JWK)를 두 번 감싼다.
- 개인키 감싸기: `wrap(privJwk, secret)` = PBKDF2(secret, salt, 210k, SHA-256) → AES-256-GCM 로 `privJwk` 암호화.
  - `enc_priv_passphrase` = wrap(priv, 패스프레이즈)
  - `enc_priv_recovery`   = wrap(priv, 복구코드)
- 복구코드: `crypto.getRandomValues` 기반 고엔트로피(예: base32 20자, 그룹 표기). **생성 직후 1회만 화면 표시**, 서버엔 감싼 개인키만.

### 글 암호화 (하이브리드, "sealed box" 등가)
- 랜덤 콘텐츠키 `CK`(AES-256-GCM)로 payload=`{ body, expectedChange }`(JSON) 암호화 → `enc_payload`(iv+ciphertext, base64).
- 각 대상 리더 `L`에 대해: ephemeral ECDH 키 생성 → `shared = ECDH(ephemeralPriv, L.pub)` → `HKDF(shared)` → AES-256-GCM 로 `CK` 감쌈. 저장: `{ accountId: L.id, ephemeralPub, wrappedCK, iv }`.
- 대상 리더 여러 명이면 리더별 항목을 배열로. 리더는 자기 항목만 골라 개인키로 `CK`를 풀고 payload 복호화.

### 알고리즘 버전
- `enc_alg = "v1:ecdh-p256+aesgcm256+hkdf-sha256+pbkdf2-210k"`. 후속 회전을 위해 태그로 둔다.

## 데이터 모델 (Supabase)

### 신규 테이블 `leader_keys`
| 컬럼 | 타입 | 비고 |
|---|---|---|
| `account_id` | text (PK, FK accounts.id) | 소유 리더 |
| `public_key` | text | JWK(base64). anon 읽기 허용(공개키) |
| `enc_priv_passphrase` | text | 패스프레이즈로 감싼 개인키 |
| `enc_priv_recovery` | text | 복구코드로 감싼 개인키 |
| `salt_pass` | text | PBKDF2 salt |
| `salt_recovery` | text | PBKDF2 salt |
| `alg` | text | 버전 태그 |
| `created_at` | timestamptz | |

- 개인키는 **암호문**이라 anon 노출돼도 무의미. 단, 최소권한 원칙으로 `enc_priv_*`·`salt_*` 는 **소유자 외 SELECT 를 RLS 로 제한**(가능하면). 최소한 `public_key` 만 anon 읽기.

### `issues` 컬럼 추가
| 컬럼 | 타입 | 비고 |
|---|---|---|
| `encrypted` | boolean default false | 암호화 글 여부 |
| `enc_payload` | text | 암호문(body+expectedChange) |
| `enc_keys` | jsonb | 리더별 감싼 CK 배열 |
| `enc_alg` | text | 버전 |

- 암호화 글은 기존 `body`·`expected_change` 를 **빈 값/NULL** 로 저장(평문 미보관). 목록/미리보기엔 제목·카테고리·상태만 노출.
- `title` 은 평문 유지(목록 표시용). 민감정보를 제목에 넣지 말라는 안내 문구 추가.

## 프론트엔드 구조

새 모듈 `src/crypto/`:
- `issueCrypto.ts` — 키 생성/감싸기/풀기, 글 암호화/복호화, 복구코드 생성. 순수 함수 + 단위테스트.
- `leaderKeyStore.ts` — `leader_keys` 로드/업서트(anon), 세션 내 복호화된 개인키 메모리 캐시.

UI:
- **리더 키 설정**(`LeaderKeySetup`): 최초 열람 시도 시 모달 — 패스프레이즈 설정 → 키 생성 → 복구코드 1회 표시(복사/저장 확인 체크) → 업로드.
- **Intake 제출**: 대상 리더 공개키 조회 → 있으면 암호화 저장(+"암호화됨" 배지), 없으면 평문 폴백(+"암호화 미적용" 안내). 암호화 글은 `/api/review` 호출 스킵.
- **LeaderInbox / Intake 열람**: 암호화 글은 패스프레이즈 입력(세션 1회) → 복호화 표시. 개인키 미설정 리더에겐 키 설정 유도.

## 에러 처리 / 엣지

- 대상 리더 키 없음 → 평문 폴백(비반적), 사용자에게 명시.
- 패스프레이즈 오입력 → AES-GCM 복호화 실패 → "패스프레이즈가 올바르지 않아요" (복구코드 경로 안내).
- 복구코드 분실 + 패스프레이즈 분실 → 그 리더에게 온 암호화 글은 복구 불가(설계상 수용). 키 재설정 시 **이후** 글만 읽힘. UI에 경고.
- 다중 대상: `enc_keys` 에 리더별 항목. 한 명이라도 키 있으면 암호화(키 없는 리더는 그 글 못 읽음 — 목록엔 뜨되 열람 시 "이 글은 회원님 키로 암호화되지 않았어요").
- **익명 작성자 본인 조회**: 접수번호+조회코드로 조회 시 상태·리더 답변은 보이나 **암호화된 본문은 재표시하지 않는다**("본문은 암호화되어 안전 보관 중"). 작성자는 본문을 이미 알고, 조회코드는 평문 저장이라 이를 복호화 키로 쓰면 운영자 불가독이 깨지기 때문. (조회코드 기반 본문 복호화는 조회코드 평문 저장 제거와 함께 후속 과제.)
- 부분 실패(암호화 중 예외) → 제출 차단하고 재시도 유도(평문으로 조용히 새지 않게).

## 테스트

## 범위 밖 (후속)

- 리더 답변(`leaderReply`)·익명 조회코드 암호화 — 이번엔 **제보 본문 기밀성**에 집중. 답변 암호화는 별도 설계.
- 키 회전/폐기, 다기기 개인키 동기화(현재는 기기+패스프레이즈, 복구코드로 재설정).
- 기존 10건 평문 마이그레이션(이미 노출됐고 사용자가 유지 선택).
- 네이티브(iOS/Android) 반영 — 웹 확정 후.
